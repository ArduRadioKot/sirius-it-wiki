# Коллекции Python и сложность операций · 20 октября

Одна и та же проверка `x in collection` может быть линейным просмотром или быстрым поиском по хешу. Поэтому коллекцию выбирают **по операциям, которые программа выполняет чаще всего**: доступ по индексу, поиск, добавление, удаление или извлечение минимума. Ниже — разбор лекции с работающими примерами Python, схемами и вопросами. Оценки относятся прежде всего к CPython; «в среднем» и «амортизированно» не означают гарантированное время каждой отдельной операции.

## 1. Как читать сложность

Если размер коллекции равен $n$, то $O(1)$ означает, что число шагов не растёт вместе с $n$; $O(n)$ — что обычно приходится просмотреть элементы; $O(\log n)$ — что область поиска многократно делится пополам. Константы тоже важны: для малого $n$ структура с лучшей асимптотикой не обязана побеждать по времени.

| Оценка | Идея | Пример |
| --- | --- | --- |
| $O(1)$ | прямой доступ | `a[i]`, `len(a)` |
| $O(\log n)$ | деление области поиска | `bisect_left(a, x)` |
| $O(n)$ | просмотр или сдвиг | `x in list`, `a.insert(0, x)` |
| $O(n\log n)$ | эффективная общая сортировка | `a.sort()` |
| $O(n^2)$ | линейная работа внутри линейного цикла | поиск в растущем списке для каждого элемента |

**Худший случай** — верхняя граница для любых данных. **Средний случай** описывает типичные входы, например при удачном распределении хешей. **Амортизированная оценка** относится к длинной серии операций: редкий дорогой шаг распределяется по множеству дешёвых.

```python
from timeit import timeit

values = list(range(100_000))
lookup = set(values)  # подготовку структуры измеряем отдельно
target = 99_999

print(timeit(lambda: target in values, number=1_000))
print(timeit(lambda: target in lookup, number=1_000))
```

Оба выражения проверяют вхождение, но список идёт по элементам, а множество вычисляет позицию из хеша. Сравнивай одинаковое число запусков и помни, что замер зависит от машины, данных и версии Python.

:::quiz
question: Что означает «$O(1)$ в среднем» для поиска в `set`?
option: Обычно число шагов не растёт с размером множества, но отдельные случаи могут быть дорогими
option: Каждый поиск всегда выполняется за одинаковое число наносекунд
option: Множество просматривает все элементы подряд
answer: 1
explanation: Средняя оценка допускает коллизии и редкие перестройки таблицы; она не равна гарантии для каждого входа.
:::

## 2. `list`: быстрый индекс, дорогой сдвиг

`list` — **динамический массив ссылок**. Рядом в памяти лежат не сами произвольные объекты Python, а ссылки на них. Адрес ячейки с индексом $i$ вычисляется сразу, поэтому `a[i]` работает за $O(1)$. Список хранит запас свободных ячеек: обычный `append` кладёт ссылку в конец, а при исчерпании ёмкости выделяется новый блок и ссылки копируются. Отдельное расширение может стоить $O(n)$, но серия добавлений стоит $O(n)$, то есть **$O(1)$ амортизированно на `append`**.

![Схема списка Python: запас ячеек, быстрый append и сдвиг при вставке в начало](assets/diagrams/python-list-operations.svg)

*В конце часто есть свободное место; вставка в начало сдвигает уже лежащие ссылки.* [Открыть схему крупно](assets/diagrams/python-list-operations.svg).

```python
items = ["A", "B", "C"]
items.append("D")       # обычно O(1), амортизированно O(1)
items.insert(0, "X")    # O(n): A, B, C, D сдвигаются вправо
print(items)            # ['X', 'A', 'B', 'C', 'D']
print(items[3])         # C — O(1)
```

| Операция | Время | Причина |
| --- | --- | --- |
| `a[i]`, `a[i] = x`, `len(a)` | $O(1)$ | известен адрес ячейки или длина |
| `append(x)`, `pop()` | $O(1)$ амортизированно | работа с концом |
| `insert(0, x)`, `pop(0)`, удаление в середине | $O(n)$ | сдвиг соседних ссылок |
| `x in a`, `index(x)`, `count(x)` | $O(n)$ | последовательный просмотр |
| `a[i:j]`, `extend(k элементов)` | $O(k)$ | копирование $k$ ссылок |
| `sort()` | $O(n\log n)$ в худшем случае | сортировка Timsort |

Есть и ловушка со ссылками:

```python
bad = [[0] * 3] * 3
bad[0][0] = 7
print(bad)  # [[7, 0, 0], [7, 0, 0], [7, 0, 0]]

good = [[0] * 3 for _ in range(3)]
good[0][0] = 7
print(good)  # [[7, 0, 0], [0, 0, 0], [0, 0, 0]]
```

В `bad` три внешние ячейки указывают **на один внутренний список**. Генератор в `good` создаёт три отдельных объекта.

:::quiz
question: Почему `list.append(x)` амортизированно стоит $O(1)$, хотя иногда нужно копировать весь список?
option: Дорогие расширения происходят редко, а между ними есть много дешёвых добавлений
option: Копирование большого массива всегда выполняется за $O(1)$
option: Python никогда не выделяет новый блок памяти
answer: 1
explanation: Запас ёмкости позволяет распределить стоимость редких копирований на длинную серию append.
:::

:::quiz
question: Что произойдёт после `rows = [[0] * 2] * 2; rows[0][0] = 1`?
option: Обе строки станут `[1, 0]`
option: Изменится только первая строка
option: Возникнет ошибка индекса
answer: 1
explanation: Обе ячейки внешнего списка содержат ссылку на один и тот же внутренний список.
:::

## 3. `tuple` и `str`: неизменяемость меняет выбор

`tuple` похож на массив ссылок фиксированной длины: индекс и `len` — $O(1)$, а поиск значения — $O(n)$. Кортеж может служить ключом словаря, **если все его элементы хешируемы**. Например, координаты `(x, y)` подходят; `([1, 2], 3)` — нет, потому что внутри список.

```python
grid = {(2, 5): "занято"}
print(grid[(2, 5)])       # занято
# grid[([2, 5], 1)] = "x"  # TypeError: unhashable type: 'list'
```

`str` тоже неизменяемая. При накоплении больших строк надёжнее собирать части, а затем один раз вызывать `join`:

```python
def make_report(rows):
    parts = [f"{name}: {score}\n" for name, score in rows]
    return "".join(parts)

print(make_report([("Аня", 5), ("Борис", 4)]))
```

`join` проходит по суммарной длине результата. Наивное `text += part` в цикле **может** многократно копировать уже собранную строку и давать квадратичную работу. CPython иногда оптимизирует конкретный случай, поэтому ускорение в микрозамере не стоит считать языковой гарантией.

:::quiz
question: Какой объект можно использовать ключом `dict`?
option: `(1, 2)`
option: `([1, 2], 3)`
option: `[1, 2]`
answer: 1
explanation: Кортеж хешируем, только если хешируемы его элементы. Список не хешируется.
:::

## 4. `dict` и `set`: быстрый поиск через хеш

При поиске ключа хеш-таблица вычисляет `hash(key)`, получает начальную позицию и проверяет равенство кандидата с ключом. Если разные ключи попали в одну позицию, возникает **коллизия**: таблица ищет другую ячейку по последовательности проб. Поэтому поиск, добавление и удаление в `dict` и `set` обычно стоят $O(1)$, а при большом числе коллизий могут деградировать до $O(n)$.

![Хеш-таблица: ключ превращается в индекс, коллизия вызывает дополнительные проверки](assets/diagrams/python-hash-table.svg)

*Хеш указывает, где начать поиск; совпадение ключей дополнительно проверяется сравнением.* [Открыть схему крупно](assets/diagrams/python-hash-table.svg).

`set` хранит уникальные хешируемые элементы, `dict` связывает ключи со значениями. Словарь сохраняет порядок вставки ключей; порядок элементов множества использовать как договорённость нельзя.

```python
names = ["Аня", "Борис", "Аня", "Вера"]
seen = set()
unique = []

for name in names:
    if name not in seen:  # O(1) в среднем
        seen.add(name)
        unique.append(name)

print(unique)  # ['Аня', 'Борис', 'Вера']
# Короткая запись с тем же сохранением порядка:
print(list(dict.fromkeys(names)))
```

Построение множества из $n$ хешируемых элементов обычно стоит $O(n)$. Пересечение `a & b` для двух множеств обычно перебирает меньшее из них и проверяет элементы в большем: $O(\min(|a|,|b|))$ в среднем. Объединение `a | b` требует пройти оба множества: $O(|a|+|b|)$. За быстрый поиск приходится платить дополнительной памятью для таблицы.

> Правило для собственных классов: если два объекта считаются равными, их хеши должны совпадать. Не меняй поля, от которых зависят хеш и равенство, пока объект хранится как ключ или элемент множества.

:::quiz
question: Почему поиск в `dict` может стать линейным?
option: Из-за множества коллизий, когда приходится проверять много кандидатов
option: Потому что словарь всегда перебирает ключи по порядку вставки
option: Потому что доступ по ключу сначала сортирует все элементы
answer: 1
explanation: Среднее O(1) предполагает, что хеши распределяют ключи достаточно хорошо. Коллизии добавляют проверки.
:::

## 5. `deque` и словарные помощники

`collections.deque` хранит элементы в последовательности небольших блоков. У обоих концов есть быстрый доступ: `append`, `appendleft`, `pop`, `popleft` — $O(1)$. Поиск или индексирование в середине — $O(n)$. Поэтому `deque` подходит для очереди FIFO, где элементы добавляют справа и забирают слева.

![Двусторонняя очередь deque: постоянное время на краях и проход к середине](assets/diagrams/python-deque.svg)

*`popleft()` не сдвигает все оставшиеся элементы, в отличие от `list.pop(0)`.* [Открыть схему крупно](assets/diagrams/python-deque.svg).

```python
from collections import deque

tasks = deque(["скачать", "проверить"])
tasks.append("сохранить")
while tasks:
    print(tasks.popleft())  # скачать, проверить, сохранить

recent = deque(maxlen=3)
for event in ["A", "B", "C", "D"]:
    recent.append(event)
print(list(recent))          # ['B', 'C', 'D']
```

Полезные надстройки над словарём:

```python
from collections import Counter, defaultdict

words = ["кот", "пёс", "кот", "рыба", "кот", "пёс"]
counts = Counter(words)
print(counts.most_common(2))  # [('кот', 3), ('пёс', 2)]

groups = defaultdict(list)
for word in words:
    groups[word[0]].append(word)
print(groups["к"])            # ['кот', 'кот', 'кот']
```

`Counter` подсчитывает частоты, `defaultdict(list)` создаёт пустой список при первом обращении к отсутствующему ключу. `OrderedDict` дополнительно умеет быстро передвигать ключ в конец через `move_to_end` — это пригодится в домашней задаче про LRU-кэш.

:::quiz
question: Чем заменить `queue.pop(0)` внутри цикла обработки очереди?
option: `deque.popleft()`
option: `list.insert(0, x)`
option: `sorted(queue)[0]`
answer: 1
explanation: popleft удаляет элемент с левого края за O(1); pop(0) сдвигает оставшиеся элементы списка.
:::

## 6. `heapq`: быстро взять минимум

**Минимальная куча** поддерживает правило: значение родителя не больше значений детей. Это не отсортированный массив, зато минимальный элемент всегда находится в `heap[0]`. `heapq` хранит кучу прямо в обычном списке: для элемента с индексом $i$ дети находятся по индексам $2i+1$ и $2i+2$.

![Минимальная куча как дерево и как массив](assets/diagrams/python-min-heap.svg)

*В дереве каждый родитель не больше своих детей; в памяти те же элементы лежат в списке.* [Открыть схему крупно](assets/diagrams/python-min-heap.svg).

```python
import heapq

jobs = []
heapq.heappush(jobs, (3, "обычная задача"))
heapq.heappush(jobs, (1, "срочная задача"))
heapq.heappush(jobs, (2, "средняя задача"))

print(jobs[0])              # (1, 'срочная задача') — O(1)
print(heapq.heappop(jobs))  # (1, 'срочная задача') — O(log n)
```

Вставка и извлечение минимума стоят $O(\log n)$: элемент поднимается или опускается по высоте дерева. Превращение готового списка в кучу через `heapq.heapify(a)` стоит $O(n)$.

:::quiz
question: Нужно многократно добавлять задачи и брать задачу с наименьшим приоритетным числом. Что выбрать?
option: `heapq`
option: `list.pop(0)` у несортированного списка
option: `tuple` без дополнительных структур
answer: 1
explanation: Куча даёт O(log n) на добавление и извлечение минимума, не требуя сортировать весь список после каждого шага.
:::

## 7. `bisect`: найти место быстро, вставить — сдвинуть

`bisect_left` ищет позицию в **уже отсортированном** списке за $O(\log n)$. Функция `insort` сначала находит позицию тем же способом, а затем вставляет элемент в `list`. Сдвиг хвоста стоит $O(n)$, поэтому вся вставка — $O(n)$.

![Двоичный поиск быстро находит место, но вставка в отсортированный список сдвигает элементы](assets/diagrams/python-bisect-insert.svg)

*Быстрый поиск места не отменяет стоимость изменения массива.* [Открыть схему крупно](assets/diagrams/python-bisect-insert.svg).

```python
from bisect import bisect_left, insort

scores = [10, 20, 30, 40]
position = bisect_left(scores, 25)
print(position)  # 2 — поиск O(log n)
insort(scores, 25)
print(scores)    # [10, 20, 25, 30, 40] — вся вставка O(n)
```

:::quiz
question: Почему `bisect.insort(a, x)` оценивается как $O(n)$?
option: Поиск места стоит O(log n), но вставка сдвигает часть списка за O(n)
option: Двоичный поиск сам просматривает все n элементов
option: insort каждый раз полностью сортирует список
answer: 1
explanation: Общую стоимость определяет более дорогой шаг — сдвиг элементов динамического массива.
:::

## 8. Найди скрытый квадрат

Частая ошибка — поместить операцию $O(n)$ внутрь цикла по $n$ элементам. Тогда получится $O(n^2)$. На слайдах приведены четыре ситуации:

| Задача | Медленный шаг | Подходящая замена |
| --- | --- | --- |
| убрать повторы с сохранением порядка | `x in unique`, где `unique` — список | отдельный `seen: set` |
| обработать очередь | `queue.pop(0)` | `deque.popleft()` |
| найти общие элементы | `x in b`, где `b` — список | один раз создать `b_set = set(b)` |
| собрать текстовый отчёт | `report += part` в цикле | накопить части и вызвать `join` |

```python
a = [1, 2, 3, 2]
b = [2, 4]
b_set = set(b)                  # O(len(b)) в среднем
common = [x for x in a if x in b_set]  # O(len(a)) в среднем
print(common)                   # [2, 2]: повторы из a сохранены

rows = [("Аня", 5), ("Борис", 4)]
parts = [f"{name}: {score}\n" for name, score in rows]
report = "".join(parts)
print(report)
```

Для первого выражения итоговая средняя оценка — $O(|a|+|b|)$; построение `b_set` входит в стоимость. Если элементы нельзя хешировать, потребуется другой способ поиска.

:::quiz
question: В цикле `for x in a: if x in b:` оба списка имеют длину n. Какова типичная верхняя оценка?
option: $O(n^2)$
option: $O(1)$
option: $O(\log n)$
answer: 1
explanation: Проверка вхождения в список может просмотреть n элементов, и она выполняется n раз.
:::

## 9. Шпаргалка для выбора коллекции

| Что нужно часто делать | Выбор | Ключевая стоимость |
| --- | --- | --- |
| Доставать по числовому индексу, добавлять в конец | `list` | индекс $O(1)$, `append` $O(1)$ амортизированно |
| Хранить неизменяемую запись или составной ключ | `tuple` | индекс $O(1)$; ключом бывает при хешируемых полях |
| Проверять уникальность | `set` | `x in s`, `add` в среднем $O(1)$ |
| Искать значение по ключу | `dict` | `d[key]` в среднем $O(1)$ |
| Добавлять и удалять с обоих концов | `deque` | оба края $O(1)$ |
| Часто брать наименьший элемент | `heapq` | извлечение $O(\log n)$ |
| Искать позицию в редко меняющемся отсортированном списке | `list` + `bisect` | поиск $O(\log n)$, вставка $O(n)$ |

**Вывод:** сначала выпиши операции и частоту их вызовов, затем выбери устройство хранения. Быстрый поиск обычно требует дополнительной памяти или ограничений на элементы.
